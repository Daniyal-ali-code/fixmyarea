# FixMyArea — UI Audit

- **Repo:** `github.com/Daniyal-ali-code/fixmyarea` (Daniyal Ali's repo), local copy `~/workspace/fixmyarea`
- **HEAD audited:** `7281274` ("Split password reset into verify code, then new password")
- **Scope:** `client/src` only — static code audit, read-only, no code changed.
- **Method:** read every page + shared component; grepped class strings for drift. No live render: no DB, no SMTP, no login available here (see §6), so nothing below is screenshot-verified.

## 2. Design tokens — what actually exists

`client/package.json`: **no `gsap`, no `framer-motion`, no animation library at all.** Deps are Next 16.4.5, React 19, Tailwind v4 (`tailwindcss@^4` + `@tailwindcss/turbopack`), Leaflet + react-leaflet, Supabase JS, bcrypt, jsonwebtoken, nodemailer, pg. Only motion in the codebase is Tailwind `transition` / `animate-pulse` (skeletons) / `active:scale-95` (one button).

`client/src/app/globals.css` (29 lines) — the entire token layer:

- `@import "tailwindcss"` (Tailwind v4, no config file, no `@theme` tokens beyond the two below).
- `--color-background / --color-foreground` only; `--font-sans: Inter…`; `--font-mono`. **No `--font-serif` in `@theme`** — Lora is loaded in `layout.js` as `--font-serif` via `next/font`, so `font-serif` depends on that variable landing, not on a declared token. Verify it actually renders Lora (not Tailwind's default Georgia stack) after the rebuild.
- **No tokens at all for:** accent colour, radius, shadow, spacing scale, card style, button style, input style. Everything is copy-pasted Tailwind classes per file — which is why the drift in §4 exists.
- Dark mode: `@custom-variant dark (&:where(.dark, .dark *))` (class-based) **plus** a `@media (prefers-color-scheme: dark)` block that sets `:root --background: #0a0a0a`. The two mechanisms disagree: toggling dark while the OS is light leaves `--background` white, so `body` behind `main` is white in dark mode. Pick one mechanism.
- No `viewport` / `theme-color` export in `layout.js` (`metadata` is title + description only) — no explicit mobile viewport or theme-color for the bottom-nav chrome.

De-facto system (inferred, not tokenised — the rebuild should tokenise exactly this, then fix the exceptions):

|---|---|---|
| Page bg | `bg-amber-50` light / `bg-stone-900` dark, on every `<main>` | |

| Border | `border-stone-300` / `dark:border-stone-700` (cards); `border-stone-400` / `dark:border-stone-600` (inputs, secondary buttons) | Two border greys, used inconsistently (see §4) |

## 3. Mobile-app shell — what's good, what's missing

**Already good — keep:**
- `BottomNav` (`components/BottomNav.js`): fixed bottom bar, `z-50`, `bg-amber-50 dark:bg-stone-900`, top border, `shadow-[0_-2px_12px_rgba(0,0,0,0.08)]`, `pb-[env(safe-area-inset-bottom)]`. Guest tabs Home / Reports / Login; signed-in Home / Reports / centre action / My Reports. Centre action is role-aware: raised 56px amber circle (`w-14 h-14 rounded-full … -top-6 ring-4`) — "+ Report" for users, shield "Admin" for admins. Active tab amber + `font-semibold` + `aria-current="page"`. Inline SVG icons, no icon lib.
- `Header` (`components/Header.js`): slim sticky top bar, `z-40`, wordmark + theme toggle + name + Logout. Correctly minimal now that nav lives at the bottom.
- Root layout bottom padding exists, so page content is not hidden behind the nav in the normal flow.

**Missing / wrong:**
1. **Layout bottom padding is 7rem on every page** (`layout.js:44`, `pb-[calc(7rem+env(safe-area-inset-bottom))]`). The nav is ~56px + safe-area; 112px is ~2× what's needed and leaves a large dead band at the bottom of every page — worst on short pages (auth, 404, empty states). It also breaks vertical centring: auth pages use `min-h-screen flex items-center justify-center` *inside* that padded wrapper, so the card sits visibly above centre. Fix: `pb-[calc(4.5rem+env(safe-area-inset-bottom))]` (~72px) and re-check auth centring.
2. **Footer + layout padding double up.** Pages with a footer (`/`, `/reports`, `/reports/[id]`, `/reports/new`) add `mt-12` on the footer *and* get the 7rem layout padding below it — ~160px of dead space at the bottom. Pages without a footer get only the padding. Unify: footer (if kept) should be the last element with no extra layout padding, or drop `mt-12`.
3. **No max-width discipline on desktop.** Content widths are all different (see §4, fix #3): `max-w-2xl` (new), `max-w-4xl` (detail, home hero), `max-w-6xl` (most), `max-w-7xl` (admin only), `max-w-md` (auth cards). Header is `max-w-6xl`, BottomNav inner grid is `max-w-3xl` — on desktop the tabs sit in a narrow centred cluster while the header/content span 6xl, so the bar reads as a floating phone UI inside a wide page. Decide one desktop container (recommend `max-w-6xl` for content + header, `max-w-3xl` only if the nav is deliberately phone-width — and if so, centre it as a floating pill, not a full-width bar with a 3xl grid).
4. **Header has no safe-area handling** (`Header.js:19`, `sticky top-0`, no `pt-[env(safe-area-inset-top)]`). BottomNav handles the bottom inset; the top inset is unhandled (notch / Dynamic Island overlap on iOS).
5. **No `viewport` / `theme-color` metadata** in `layout.js` — add `export const viewport = { viewportFit: "cover", themeColor: … }` (light/dark) so the safe-area insets and the amber/stone chrome actually apply on iOS/Android.
6. **BottomNav flash on load:** while `AuthProvider` is still loading (`user === null`), the guest tab bar renders, then swaps to the 4-tab signed-in bar — a visible tab-bar jump + layout shift on every signed-in load. Render a neutral placeholder (or nothing) until auth resolves.
7. **Admin has no bottom-nav parity issue, but:** the admin centre tab is a shield labelled "Admin" that links to `/admin` — fine — but there is no "My Reports"/profile tab for admins and no way back to `/dashboard` (admins are redirected away from it). Acceptable if intentional; note it.
8. **Desktop stretching:** on ≥1280px the home/reports grids go 3-col at `max-w-6xl` (fine), but the home map is a fixed 520px tall full-width block and the hero is `py-20` — the page reads as a stretched phone layout, not a desktop layout. The rebuild should cap content width *and* give the hero/map a desktop treatment, not just centre the phone layout.
